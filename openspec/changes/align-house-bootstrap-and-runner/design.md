## Context

The global house-style pack currently owns `house-init`, `house-adopt`, `house-new`, `house-apply`, and `house-archive`. `house-init` and `house-adopt` initialize OpenSpec when needed but preserve whatever project-local OpenCode scaffolding happens to exist. `house-new` independently recreates proposal generation behavior that supported OpenSpec releases supply through `opsx-propose`.

OpenSpec 1.4.1 has been verified with profile `core` and delivery `both`. In that configuration it generates five project-local OpenCode commands and five project-local skills. The workflow requires a supported release with equivalent behavior: initialization adds missing OpenCode integration to an existing root, and forced update regenerates the selected integration.

The current `agents/runner.md` is Android- and Gradle-specific. It permits a formatter and describes source mutation despite denying edit permission. The house apply flow invokes checks directly and has no reporting contract for failures.

## Goals / Non-Goals

**Goals:**

- Ensure fresh and existing house-style projects receive project-local OpenCode core commands and skills generated by OpenSpec.
- Make standard `opsx-explore` and `opsx-propose` workflows the brainstorming and apply-ready proposal entry points.
- Preserve `house-new` as a compatibility alias during migration.
- Keep only the hand-authored global `openspec-house-style` skill after local generation is proven.
- Define Runner as a framework-agnostic, read-only source verification agent.
- Use Runner for targeted checks and final verification in `house-apply`.
- Provide runnable, isolated checks for bootstrap, regeneration, prohibited Runner behavior, report structure, and house-apply routing.

**Non-Goals:**

- Change OpenSpec CLI behavior or generated templates.
- Remove `house-new` in this change.
- Replace `house-apply` or `house-archive` with generated `opsx-apply` or `opsx-archive`.
- Give Runner permission to edit source, fix failures, format files, install dependencies, deploy software, or start services.
- Select test commands when a repository does not define them.
- Migrate or rewrite existing OpenSpec changes.

## Decisions

### Decision: Use OpenSpec as the only generator for project-local core integration

`house-init` and `house-adopt` will invoke a supported OpenSpec release with the OpenCode tool and command-local `--profile core`. Each command will save the current global delivery value, set delivery to `both` only when needed for generation, and restore the saved value before returning on success or failure. The workflow will use `openspec init <root> --tools opencode --profile core` for a fresh root and may use the same command for an existing root that lacks OpenCode integration. It will use `openspec update --force <root>` when the selected OpenCode integration exists but must be regenerated. These operations are verified on OpenSpec 1.4.1.

The commands will preserve unrelated project files and OpenSpec changes. They will set `openspec/config.yaml` to `schema: house-style` while preserving other keys. They will verify the expected five generated commands and five generated skills instead of maintaining duplicate templates in the house pack.

### Decision: Make standard proposal entry points primary

`/opsx-explore` will be the optional brainstorming entry point. `/opsx-propose` will generate the apply-ready `proposal`, `design`, `specs`, `tasks`, and `plan` artifacts under the configured `house-style` schema. The higher-priority global `AGENTS.md` rule will replace the generated `/opsx-apply` next-step suggestion with `/house-apply`, including when the user directly invokes `/opsx-propose`. `/house-apply` and `/house-archive` will remain the only implementation and closeout routes because they add the house test-first, review, verification, retrospective, commit, and sync rules; generated `/opsx-apply` and `/opsx-archive` commands will not be used for those stages.

`house-new` will remain as a compatibility alias that delegates to the same `/opsx-propose` artifact-generation behavior. It will override only the generated next-step handoff so users are directed to `/house-apply`, not `/opsx-apply`.

### Decision: Remove global generated skills only after local generation passes

The implementation will first prove generation in isolated fresh and existing roots. It will then remove the global generated copies at `skills/openspec-propose/`, `skills/openspec-explore/`, `skills/openspec-apply-change/`, and `skills/openspec-archive-change/`. It will keep `skills/openspec-house-style/` because that skill contains hand-authored policy used by the global house commands.

This order prevents a gap where neither global nor project-local generated skills are available.

### Decision: Discover and run repository-defined verification commands

Runner will inspect repository-owned sources such as `AGENTS.md`, package scripts, build files, task files, and CI configuration to identify commands for the requested verification scope. It may run repository-defined unit tests, integration tests, builds, lint, validation, inspection, and configuration checks. Its `bash` permission will require user approval, while edit and task permissions remain denied. It must not invent commands or broaden a targeted request without reporting the additional scope.

Runner must not run formatters, dependency installation, clean commands, deployment, release publication, migrations, database mutations, service or container startup, device or emulator startup, or any command that edits source or managed configuration, even with approval. Build outputs and test reports remain allowed. If a required check depends on a prohibited preparation step, Runner will report the check as blocked and return that action to the orchestrator.

### Decision: Use a fixed verification report contract

For every command, Runner will report the exact command and exit code. For each failure, it will report the failure class, test or check identifier, `file:line` when available, a bounded evidence excerpt, known cascade failures, and one next action. Failure classes will distinguish at least test, integration, build, lint, and environment or command failures.

Runner will identify a cascade only when output shows that one primary failure caused later failures or skipped checks. It will not present repeated downstream messages as independent root causes. Evidence must be sufficient to locate the failure but must not reproduce an unbounded command log.

### Decision: Runner verifies; implementation agents fix

`house-apply` will delegate each slice's targeted verification and the post-review final verification to Runner. If Runner reports a source or test failure, the orchestrator will return the bounded failure report to an implementation agent. Runner will rerun the affected check after the fix. The workflow will not ask Runner to design or apply a fix.

Final verification will remain gated on a clean review loop. `house-apply` will record Runner's exact commands, exit codes, and outcome in `verify.md`.

### Decision: Verify behavior in isolated fixtures and prompt smoke checks

Bootstrap checks will create temporary fresh and existing OpenSpec roots under a temporary home so profile and delivery settings do not modify the user's active projects. The check will fingerprint the real global OpenSpec config before and after isolated CLI operations. It will assert the generated command and skill counts, statically confirm the command contracts assign `schema: house-style` and save and restore delivery, verify that an existing unrelated sentinel survives generation, remove one generated asset, run `openspec update --force`, and confirm regeneration. The smoke harness executes OpenSpec CLI operations plus static command-contract assertions; it does not execute Markdown commands.

The smoke script will inspect the Runner contract without invoking a model. It will verify required frontmatter, supported check types, required report fields, prohibited responsibilities, and non-passing failed or blocked outcomes. Its apply mode will verify that targeted and final checks route to Runner in order and fixes route to implementation agents.

## Risks / Trade-offs

- OpenSpec delivery is a global CLI setting in 1.4.1. Bootstrap commands must restore its saved value on success and failure. Isolated verification fingerprints the real config to detect pollution.
- Generated file names are owned by OpenSpec. Count and location checks are less brittle than copying generated content into tests, but they can miss an unexpected replacement with the same count; smoke checks should also assert the expected core workflow names.
- `house-new` remains temporarily, so two user-facing names lead to one proposal flow. This is intentional compatibility debt and can be removed in a later change.
- Framework-agnostic command discovery cannot guarantee that every repository documents all checks. Runner will report missing definitions instead of guessing or installing tooling.
- Integration tests sometimes require services. Runner will run them only when the repository-defined command does not require Runner to start a service; otherwise it will report a blocked check and the required external precondition.
